# ML engineering portfolio

Four self-contained machine learning projects. Each one runs end to end on a
laptop CPU in under three minutes, has a test suite, and is written around a
decision someone would actually have to make — not around a leaderboard score.

> **All four use synthetic data**, generated by code in the repository. That is
> a deliberate trade: it means the feature engineering, the leakage tests and
> the evaluation protocols are inspectable and reproducible, rather than hidden
> behind a Kaggle download of anonymised PCA components. It also means **none
> of the numbers are evidence about a real business**. Each README says so at
> the top, and says which parts transfer.

## The projects

| Project | Problem | The part worth reading |
|---|---|---|
| [fraud-detection](fraud-detection/) | Card fraud at a 0.17% base rate | Choosing the alert threshold by pricing the two error types, and why `scale_pos_weight` made the model *worse* |
| [demand-forecasting](demand-forecasting/) | 28-day SKU demand, 60 SKUs | Every lag derives from the horizon, so `lag_1` cannot be built at a 28-day horizon |
| [semantic-similarity](semantic-similarity/) | Duplicate question detection | The split protocol moves the score more than the model does — and changes which model you would pick |
| [recommender-system](recommender-system/) | Implicit-feedback recommendations | Implicit ALS from scratch, and why accuracy alone picks the wrong model |

## Headline results

Each is reproducible with `python -m src.train` in the project directory.

**Fraud detection** — 48k held-out transactions, 97 frauds:

| Model | PR-AUC | Net savings vs approving everything |
|---|---|---|
| Rule baseline (the incumbent) | 0.301 | 46% |
| Logistic regression | 0.506 | 53% |
| LightGBM | **0.754** | **60%** |
| LightGBM + `scale_pos_weight` | 0.399 | 59% |

**Demand forecasting** — six rolling origins, 28 days each:

| Model | WAPE | Value add vs seasonal naive |
|---|---|---|
| LightGBM (Tweedie) | **0.387** | **+36%** |
| Moving average, 28d | 0.476 | +22% |
| Seasonal naive | 0.606 | — |

**Semantic similarity** — same models, same data, two splitting protocols:

| Model | Random pair split | Cluster-disjoint split |
|---|---|---|
| Logistic regression | 0.786 | 0.794 |
| LightGBM | 0.886 | 0.788 |

Under the leaky protocol LightGBM looks 10 points better than logistic
regression. Under the honest one they are tied.

**Recommender** — 4,000 users, full-catalogue ranking:

| Model | Recall@10 | Catalogue coverage |
|---|---|---|
| Item-kNN | **0.1251** | 0.350 |
| ALS | 0.1136 | **0.569** |
| Popularity | 0.0527 | 0.017 |

## What these have in common

Each project is built around one failure that does not announce itself — the
kind that produces a *better* offline metric and a worse system:

- **Fraud**: a feature built with a `groupby` over the whole table leaks the
  future into the past. `tests/test_features.py` asserts that features
  recomputed on a truncated log reproduce the rows already there.
- **Forecasting**: a lag shorter than the horizon does not exist at scoring
  time. The horizon is an argument to the feature builder so the bad lag cannot
  be requested.
- **Similarity**: questions recur across pairs, so a random split puts the same
  question on both sides. `assert_no_question_overlap` raises on it.
- **Recommender**: scoring items the user has already played inflates every
  metric. The mask is asserted, and the inflation is demonstrated.

Other shared conventions:

- **Every model is compared against the baseline it would actually replace** —
  a rule engine, seasonal naive, a popularity chart — not against random.
- **Thresholds and hyperparameters are chosen on validation data** and frozen
  before the test set is touched.
- **Metrics are chosen for the decision**: PR-AUC and dollar cost at a 0.17%
  base rate, WAPE rather than MAPE on a mixed-velocity catalogue, ranking
  metrics rather than RMSE on implicit feedback.
- **Each README ends with what the project does not do.**

## Running anything

Python 3.10+. One shared dependency set, no GPU:

```bash
pip install -r requirements.txt

cd fraud-detection        # or any of the four
python -m src.train       # full run
python -m pytest tests -q # test suite
```

Every training script takes `--help`, and the flags that change conclusions —
`--separability`, `--horizon`, `--hard-negative-share`, `--taste-sharpness` —
are documented in each project's README.

| Project | Full run | Tests |
|---|---|---|
| fraud-detection | ~25s | 24 tests, ~11s |
| demand-forecasting | ~2m10s | 35 tests, ~61s |
| semantic-similarity | ~50s | 35 tests, ~27s |
| recommender-system | ~20s | 37 tests, ~6s |

131 tests in total, all CPU-only. GitHub Actions runs each project's suite on
every push, plus a cut-down training run of each entry point.

Training runs write to `<project>/artifacts/`: a `metrics.json` containing
every number quoted in the README, plus evaluation plots. That directory is
gitignored — the numbers in each README are reproducible, not committed.
