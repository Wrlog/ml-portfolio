# ML engineering portfolio

Four small machine learning projects. Each runs on a laptop CPU in under three
minutes, has a test suite, and is built around a practical decision rather
than a leaderboard score.

All four use synthetic data generated by code in the repo, so none of the
numbers are evidence about a real business. The upside is that the feature
engineering, leakage tests and evaluation can all be read and rerun, which a
Kaggle download of anonymised PCA components doesn't allow. Each README says
which parts transfer.

## Projects

| Project | Problem | What to look at |
|---|---|---|
| [fraud-detection](fraud-detection/) | Card fraud at a 0.17% base rate | Choosing the alert threshold by pricing the two error types, and why `scale_pos_weight` made the model *worse* |
| [demand-forecasting](demand-forecasting/) | 28-day SKU demand, 60 SKUs | Every lag derives from the horizon, so `lag_1` cannot be built at a 28-day horizon |
| [semantic-similarity](semantic-similarity/) | Duplicate question detection | The split protocol moves the score more than the model does, and changes which model you would pick |
| [recommender-system](recommender-system/) | Implicit-feedback recommendations | Implicit ALS from scratch, and why accuracy alone picks the wrong model |

## Results

Run `python -m src.train` in a project directory to reproduce these.

Fraud detection, 48k held-out transactions, 97 frauds:

|---|---|---|
| Rule baseline (the incumbent) | 0.301 | 46% |
| Logistic regression | 0.506 | 53% |
| LightGBM | **0.754** | **60%** |

## Common threads

Each project has one mistake that would improve the offline metric and make
the real system worse, plus a test for it:

- Fraud: a `groupby` over the whole table leaks the future into the past.
  `tests/test_features.py` checks that features recomputed on a truncated log
  reproduce the existing rows.
- Forecasting: a lag shorter than the horizon doesn't exist at scoring time.
  The feature builder takes the horizon as an argument, so it can't be asked
  for one.
- Similarity: questions recur across pairs, so a random split puts the same
  question on both sides. `assert_no_question_overlap` raises on it.
- Recommender: scoring items the user has already played inflates every
  metric. The mask is asserted and the inflation is measured.

Models are compared with the baseline they'd replace (a rule engine, seasonal
naive, a popularity chart), not with random. Thresholds and hyperparameters
are picked on validation data and frozen before the test set is touched.
Metrics fit the decision: PR-AUC and dollar cost at a 0.17% base rate, WAPE
over MAPE for a mixed-velocity catalogue, ranking metrics over RMSE for
implicit feedback. Each README ends with what the project doesn't do.

## Running it

Python 3.10+. One shared dependency set, no GPU:

```bash
pip install -r requirements.txt

cd fraud-detection        # or any of the four
python -m src.train       # full run
python -m pytest tests -q # test suite
```

Every training script takes `--help`. The flags that change conclusions
(`--separability`, `--horizon`, `--hard-negative-share`, `--taste-sharpness`)
are covered in each project's README.

| Project | Full run | Tests |
|---|---|---|
| fraud-detection | ~25s | 24 tests, ~11s |
| demand-forecasting | ~2m10s | 35 tests, ~61s |
| semantic-similarity | ~50s | 35 tests, ~27s |
| recommender-system | ~20s | 37 tests, ~6s |

131 tests in total, all CPU-only. GitHub Actions runs every suite on each
push, plus a cut-down training run of each entry point.

Training writes `<project>/artifacts/metrics.json` (every number quoted in the
README) and evaluation plots. That directory is gitignored; the numbers come
from rerunning the code.
